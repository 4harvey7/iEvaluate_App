DEFECT LOG - 31 AUGUST 2026

Ordered most severe first.

--------------------------------------------------------------------------------
DEF-01  The word "Semester" is printed twice on the official report
        SEVERITY: HIGH        STATUS: FIXED 31/08/2026, PENDING RE-TEST
--------------------------------------------------------------------------------
  The exported PDF read "Academic Year: 1st Semester Semester 2025-2026". The
  report screen had the same fault, hidden only because the field is truncated
  there (DEF-03).

  ROOT CAUSE, CONFIRMED IN CODE
  The codebase documents its own contract in
  lib/core/services/system_settings_service.dart lines 11-12: "semester" is a
  label that ALREADY includes the word, e.g. "1st Semester", and
  "academicYear" is just "2025-2026". Two things broke that contract:

    1. Both places that compose the field inserted the word a second time:
         lib/instructor/detailed_report_screen.dart:358
         lib/core/services/pdf/pdf_service.dart:288
       Each read '$term Semester $academicYear'.
    2. lib/instructor/past_semesters_screen.dart:421-422 split the combined
       label "1st Semester 2025-2026" on the FIRST space, producing
       term="1st" and academicYear="Semester 2025-2026".

  All three entry points into the report were affected, because the dashboard
  passes term="2nd Semester" and the department-head page does the same.

  FIX APPLIED
    - Both composition sites now read '$term $academicYear', since the term
      already carries the word.
    - Past Terms now splits on the LAST token via two new helpers,
      _semesterOf() and _academicYearOf(), giving term="1st Semester" and
      academicYear="2025-2026" as the contract requires.
    - "flutter analyze" reports no issues on all three files.

  STILL TO DO: rebuild the app and re-run TC006 steps 3 and 8 to confirm the
  header now reads "1st Semester 2025-2026" both on screen and in the PDF.

--------------------------------------------------------------------------------
DEF-02  Word cloud clips words at the panel edge
        SEVERITY: MEDIUM      STATUS: FIXED 31/08/2026, PENDING RE-TEST
--------------------------------------------------------------------------------
  In "AI Word Cloud" the rotated term "Fair grading" ran past the right edge of
  the dark panel and was cut off mid-word, so it could not be read.

  Because the cloud reshuffles on every load, WHICH word was clipped changed
  between refreshes, making this intermittent rather than tied to one term.

  ROOT CAUSE, CONFIRMED IN CODE
  Nothing bounded a word to the panel. The words sit in a Wrap inside a
  fixed-padding Container, and each word was a bare Text with no width
  constraint, so a word wider than the panel simply overflowed it. Rotated
  words are the ones most at risk: RotatedBox swaps the constraints it passes
  down, so a rotated word's own text width becomes its vertical extent, and
  neither extent was capped.

  FIX APPLIED
    - The word area is now wrapped in a LayoutBuilder, so the panel's real
      inner width is known at layout time.
    - Every word is bounded by ConstrainedBox(maxWidth: that width) and drawn
      through FittedBox(fit: BoxFit.scaleDown), so a word too wide to fit is
      rendered slightly smaller instead of running off the edge. scaleDown only
      ever reduces, so no word grows beyond the size its count earned it.
    - The same bound sits inside RotatedBox, where the swapped constraints make
      it cap the rotated word's height. Both extents are now bounded, so
      clipping is impossible by construction rather than by luck of the shuffle.
    - "flutter analyze" reports no issues on the file.

  STILL TO DO: rebuild the app and re-run TC004 step 7, refreshing several
  times so more than one shuffle is checked.
  File: lib/instructor/student_feedback_screen.dart

--------------------------------------------------------------------------------
DEF-03  Report header fields are truncated on screen
        SEVERITY: MEDIUM      STATUS: FIXED 31/08/2026, PENDING RE-TEST
--------------------------------------------------------------------------------
  On "Official Evaluation Report" the identity fields were cut off:
    "Instructor Name: Rodz..."
    "Academic Year: 1st Se..."
    "Department: College o..."
  The instructor could not confirm from the screen that the report was about
  them or which term it covered.

  The exported PDF was NOT affected: it renders "Rodz Harvey Licayan" and
  "College of Technology and Engineering" in full. So this was a layout
  constraint in the on-screen header, not bad data.

  ROOT CAUSE, CONFIRMED IN CODE
  _headerField rendered the value with overflow: TextOverflow.ellipsis on a
  single line, and the header places TWO of these side by side in one Row - so
  each field had only half the screen width to work with. On a phone that is
  not enough for a full name plus its label, so every long value was cut.

  FIX APPLIED
    - The value now wraps (softWrap: true, no ellipsis) instead of being cut,
      and the Row is top-aligned so a wrapped value sits correctly beside its
      label.
    - The field grows downward by a line or two on a narrow screen. That is the
      right trade: this block exists so the instructor can confirm the report is
      theirs, so being complete matters more than being one line tall.
    - "flutter analyze" reports no issues on the file.

  STILL TO DO: rebuild the app and re-run TC006 step 3, confirming all four
  fields read in full.
  File: lib/instructor/detailed_report_screen.dart

--------------------------------------------------------------------------------
DEF-04  Direct Quotes counter sits flush against the screen edge
        SEVERITY: LOW         STATUS: FIXED 31/08/2026, PENDING RE-TEST
--------------------------------------------------------------------------------
  The "N Comments" counter beside the "Direct Quotes" heading reached the right
  edge of the display with no padding. At the tested count it stayed readable,
  but a wider value or a larger system font size would have clipped it.

  ROOT CAUSE, CONFIRMED IN CODE
  The heading and the counter sat in a spaceBetween Row as two unconstrained
  Text widgets. Neither could yield, so once the pair exceeded the row width the
  counter was pushed off the end rather than the heading giving way.

  FIX APPLIED
    - Both sides are now Flexible with a 12px gap between them, and the counter
      is end-aligned, so the heading yields first and the number is never cut.
    - "flutter analyze" reports no issues on the file.

  STILL TO DO: re-run TC004 step 8, ideally once at the largest system font
  size the device offers.
  File: lib/instructor/student_feedback_screen.dart

DEF-05  Avatar initials differ between the drawer and Settings
        SEVERITY: LOW         STATUS: FIXED 31/08/2026, PENDING RE-TEST
--------------------------------------------------------------------------------
  The same signed-in instructor was shown as "RH" in the side drawer but "RL"
  on the Settings profile card, so the account appeared to belong to two
  different people depending on the screen.

  ROOT CAUSE, CONFIRMED IN CODE
  The two screens composed the initials from different things. The drawer took
  the first TWO WORDS of the full display name, so "Rodz Harvey Licayan" gave
  "RH" - the middle name. Settings used first_name + last_name and gave "RL".

  FIX APPLIED
    - The drawer now uses a new _initialsOf() helper that takes the FIRST and
      LAST word of the name, skipping any middle name, so it produces "RL" and
      agrees with Settings. A single-word name yields one letter, and an empty
      name still yields "?".
    - Settings was already correct and is unchanged.
    - "flutter analyze" reports no issues on the file.

  STILL TO DO: re-run TC007 step 1 and confirm the drawer and the Settings
  profile card show the same two letters.

WHAT CHANGED FROM THE PREVIOUS VERSIONS OF THIS DOCUMENT

AGAINST THE 4-CASE VERSION OF 26 AUGUST 2026

1. EXPECTED RESULTS WERE WRONG ON THREE OF FOUR CASES. The old TC001-TC003 all
   ended with "The account is created successfully and the user is redirected
   to the login page" - a registration outcome carried into three view-only
   screens. Each case now states the outcome its own steps produce.

2. A LIVE PASSWORD WAS PRINTED IN THE TEST DATA. The old TC004 listed a working
   credential in a document circulated to panelists. Credentials are now
   referred to but never written down.

3. THE DOWNLOAD STEP POINTED AT THE WRONG SCREEN. The old TC002 step 4 checked
   for a download control on Past Terms, where none exists. It now runs in
   TC006 against the report screen's app bar.

4. EVERY STEP CARRIES ITS OWN EXPECTED RESULT, so a failure identifies the step
   rather than giving one verdict for the whole scenario.

5. FAILURE PATHS ARE TESTED, NOT JUST HAPPY PATHS - rate limiting,
   deactivated-account sign-in, password rules, and wrong or expired codes.
   The old version recorded Pass on every case with no negative testing.

6. RESULTS ARE NO LONGER PRE-FILLED. Only cases actually executed carry a
   verdict; the rest say NOT EXECUTED and why.

AGAINST THE 14-CASE VERSION OF 31 AUGUST 2026

7. THE SAME COVERAGE IS NOW EIGHT CASES INSTEAD OF FOURTEEN.
   Nothing was dropped. Cases that tested one screen from two angles, or the
   read and write halves of one screen, were folded together, so the document
   reads as one case per screen or flow. Where a merged case mixes a passing
   read path with an unexecuted write path, the split is stated in the Actual
   Result and marked in the steps.
