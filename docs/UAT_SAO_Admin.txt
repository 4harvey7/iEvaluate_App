HOW TO READ THIS DOCUMENT
--------------------------------------------------------------------------------
* Text in "double quotes" appears on screen exactly as written. Match it
  character for character.
* Names in [square brackets] are database tables or edge functions to check
  when a step needs back-end verification.
* Each step has its own expected result, so a failed case identifies WHICH
  step failed.
* "Actual Result" is blank where the case has not been run.

!! DESTRUCTIVE-ACTION WARNING !!
  This role can create accounts, change roles, disable users, switch the
  active term for the whole system, and rotate credentials. Cases marked
  [LIVE DATA] change real records. Run them on staging, or on throwaway
  accounts you are willing to lose, and never during a live evaluation period.

TC-A01  SIGN IN AS SAO ADMINISTRATOR AND READ THE SYSTEM OVERVIEW
================================================================================
Preconditions : App on the Login screen. Account is active with role SAO_ADMIN.
Test Data     : View only.

STEPS
 1. Sign in with the SAO administrator credentials.
    Expected: Routes to the admin landing screen titled "Dashboard", NOT any
              other role's dashboard. Bottom tabs read "Dashboard", "Users",
              "Personnel", "Analytics".
 2. Read the header card.
    Expected: Shows "SAO ADMINISTRATION", "System Overview" and the subtitle
              "Operations, evaluation progress, and account activity."
 3. Read the health strip.
    Expected: Shows "Automation" and "Database", each with a status indicator,
              plus a refresh control. Both read healthy when n8n and Supabase
              are reachable.
 4. Read the two counters.
    Expected: A count labelled "Total Users" and a count labelled "Files
              Scanned" for the current term. Both are numbers, not blank or
              "null".
 5. Cross-check "Total Users" against [user_info] / [Sao_users].
    Expected: The figure equals the number of registered accounts.
 6. Cross-check "Files Scanned" against the scan/survey records for the active
    term.
    Expected: The figure equals the count gathered this term, and changes only
              when the term changes or new scans arrive.
 7. Turn off Wi-Fi and mobile data, then tap the health-strip refresh.
    Expected: The affected indicator reports a problem rather than silently
              staying green. The app does not crash.

Expected Result : The admin lands on the System Overview, and both the health
                  indicators and the two counters reflect the real state of the
                  system.
Actual Result   : PASS on steps 1-4 (observed 31/08/2026). Dashboard rendered
                  with "SAO ADMINISTRATION" / "System Overview" / "Operations,
                  evaluation progress, and account activity.", the health strip
                  showing "Automation" and "Database" both healthy, "17 Total
                  Users" and "152 Files Scanned this term", and the four tabs
                  Dashboard / Users / Personnel / Analytics.
                  Steps 5-7 not executed.

TC-A02  APPROVE A PENDING ACCOUNT REGISTRATION                     [LIVE DATA]
================================================================================
Preconditions : At least one account has registered and is awaiting approval.
Test Data     : One throwaway registration. Edge function
                [admin-accept-user]. Tables [user_info], [Sao_users].

STEPS
 1. On the dashboard, find the "Pending Approvals" section.
    Expected: Subtitle reads "Review new accounts before granting access."
              with a "View All" link. Pending registrations are listed.
 2. When there are no pending registrations, read the empty state.
    Expected: Reads "All caught up" rather than an empty gap or a spinner that
              never resolves.
 3. Tap a pending account.
    Expected: Full details open, showing "Email Address", "Employment Status",
              "Academic Dept", "Address" and "Registered On". Fields with no
              value read "Not provided", not blank or "null".
 4. Confirm the requested role is shown and is the role the person actually
    registered for.
    Expected: The role label matches the registration, e.g. "SAO Staff (Data
              Gatherer)", "SAO Administrator", "Department Head", "Instructor".
 5. Tap "Approve".
    Expected: The account is approved via [admin-accept-user], the row leaves
              the pending list, and the user count on the dashboard increases
              by one.
 6. Have the approved person sign in.
    Expected: They can now sign in and land on the dashboard for the role they
              were approved as, and no other.
 7. Force a failure (approve with no network) and observe.
    Expected: Message reads "Action failed. Please try again." and the account
              is NOT left half-approved: it either stays pending or is fully
              approved, never both.

Expected Result : A pending registration can be reviewed in full and approved,
                  after which the person can sign in with exactly the role they
                  were approved for, and a failed approval leaves no partial
                  state.

TC-A03  CREATE AN ACADEMIC USER, INCLUDING THE DEPARTMENT HEAD
        AUTHORIZATION CODE                                         [LIVE DATA]
================================================================================
Preconditions : Signed in as SAO admin on the "Users" tab. Access to the
                admin's email inbox for the verification code.
Test Data     : A throwaway name and email. Edge functions [send-admin-code],
                [admin-create-user].

STEPS
 1. Open the "Users" tab.
    Expected: Screen lists academic users. While loading it reads "Loading
              academic users…"; with none it reads "No academic users found."
 2. Tap "Add Academic Personnel" (or "Create User").
    Expected: A form opens with "First Name", "Last Name", an email field, a
              role selector and a department selector.
 3. Submit the form with required fields left empty.
    Expected: Refused with a validation message. No account is created.
 4. Create a plain INSTRUCTOR account with valid details.
    Expected: The account is created without asking for a code, and appears in
              the list.
 5. Now create an account with the role DEPARTMENT HEAD.
    Expected: BEFORE creating anything the app states "Creating a Department
              Head requires authorization." and asks "Enter the 6-digit code
              sent to your email:". A code arrives by email.
 6. Enter an INCORRECT 6-digit code.
    Expected: Refused. NO Department Head account is created.
 7. Enter the CORRECT code.
    Expected: The Department Head account is created and appears in the list.
 8. Repeat step 5 but cancel at the code prompt.
    Expected: No account is created and no partial record is left behind.
 9. Force a server failure during creation.
    Expected: Message reads "Could not create the user. Please try again." and
              no partially-created account is left.

Expected Result : Ordinary instructor accounts can be created directly, while
                  creating a Department Head is gated behind a correct emailed
                  6-digit code, and every refusal leaves no partial account.
Actual Result   :
Comments        : This is the most security-relevant case in the module. The
                  privilege escalation guard is the thing being tested, not the
                  form.

 6. Sign in as that account again.
    Expected: Sign-in now succeeds and lands on the correct role's dashboard.

Expected Result : An account can be disabled and re-enabled by the admin, a
                  disabled account cannot sign in, and no evaluation data is
                  lost either way.

TC-A07  SUBJECT MANAGEMENT - BULK IMPORT AND MANUAL ADD            [LIVE DATA]
================================================================================
Preconditions : Drawer item "Subject Management" is reachable. The n8n bulk
                import workflow is running. A Google Sheet of subject
                assignments is prepared for the active term.
Test Data     : One prepared sheet, plus one manual subject. Webhook URL comes
                from the env var for subject bulk import.

STEPS
 1. Open the drawer and tap "Subject Management".
    Expected: The screen lists subject assignments for the active term and
              states which term that is.
 2. Use the search box and the assigned/unassigned filter.
    Expected: Search narrows the list, and the filter separates subjects that
              have an instructor from those that do not.
 3. Add ONE subject manually with valid details.
    Expected: It is created and appears in the list against the active term.
 4. Add a NEW subject reusing the code from step 3, with a DIFFERENT name.
    Expected: Refused. A dialog headed "Subject Code Already Used" names the
              subject holding that code and its department. Reopen the
              original subject afterwards and confirm its name was NOT
              rewritten - silently overwriting it is the defect this step
              exists to catch.
 5. Add a NEW subject with a different code but the SAME name as step 3.
    Expected: A dialog headed "Possible Duplicate" names the existing code.
              "Cancel" creates nothing. Repeat and choose "Create anyway" and
              it is created - one name under two codes is allowed, but only
              deliberately.
 6. Open a subject, tap Remove beside an instructor whose assignment has NO
    evaluation records.
    Expected: A progress indicator appears while it checks, then a confirm
              dialog, then the instructor is removed and the list refreshes.
 7. Repeat step 6 on an assignment that HAS evaluation records - management
    results, performance results or student remarks, any ONE of the three is
    enough.
    Expected: A dialog headed "Cannot Remove" states how many records exist.
              The delete is never attempted and the instructor is still listed
              afterwards. A case with only performance results or only remarks
              matters most here: those used to read as zero, so the app
              promised the removal was safe and the database then refused it.
 8. Open the edit sheet for an existing assignment, clear the instructor field
    and save.
    Expected: Refused, with a message pointing at the Remove button. The sheet
              must NOT close reporting success while leaving the instructor
              still assigned.
 9. Run "Import from Google Sheets" with the prepared sheet.
    Expected: The import runs via the n8n webhook, reports progress, and ends
              with a clear success or failure message - never an indefinite
              spinner.
10. Cross-check the imported rows against the sheet.
    Expected: Every row in the sheet is either imported or reported as an
              error. Nothing is silently dropped.
11. Deliberately include a bad row (unknown instructor, unknown subject) and
    re-import.
    Expected: The bad row does NOT import silently. It is recorded as an
              import error and triaged in the SAO Staff module
              (UAT_SAO_Staff TC-S08), not here.
12. Run the import with n8n stopped.
    Expected: A clear failure message. No partial import is left behind.
13. Attempt to delete a subject that already has evaluation results.
    Expected: Deletion is BLOCKED. Results already recorded against a subject
              cannot be orphaned.

Expected Result : Subjects can be added manually and in bulk, a subject code
                  can never be given to a second subject, bad rows are
                  reported rather than silently dropped, an instructor can be
                  unassigned only while no evaluation records exist, and a
                  subject carrying results cannot be deleted.
Actual Result   :
Comments        : Steps 4-5 need 20240130000018_one_subject_per_code applied;
                  without it the app still refuses, but only in Dart, so the
                  n8n import can create the duplicate anyway. Steps 7 and 13
                  need 20240130000015_protect_assignments_with_results.
                  Confirm both are applied before judging any of them.
Tester / Date   :

TC-A08  DEPARTMENT MANAGEMENT - ADD AND EDIT                       [LIVE DATA]
================================================================================
Preconditions : Drawer item "Manage Departments" is reachable.
Test Data     : One throwaway department code and name.

STEPS
 1. Open "Manage Departments".
    Expected: Screen titled "Department Management" with "Add or edit
              departments". While loading it reads "Loading departments…"; with
              none it reads "No departments yet". A counter reads
              "All Departments (n)".
 2. Tap "Add Department" and submit with fields empty.
    Expected: Refused. "Department Code *" and "Department Name *" are marked
              required, with the rule "At least 3 characters".
 3. Enter a valid code and name, then submit.
    Expected: A confirmation appears reading "Are you sure you want to add"
              with the department named, and a "Confirm Add" button. Nothing
              is created until it is confirmed.
 4. Confirm the addition.
    Expected: Message reads "Department added successfully" and the new
              department appears, with the counter increasing by one.
 5. Add a department reusing an existing department NAME, with a new code.
    Expected: Refused BEFORE the confirmation dialog appears. An alert headed
              "Department Already Exists" names the department holding it and
              says the NAME is what clashed. No row is created.
 6. Add a department reusing an existing department CODE, with a new name.
    Expected: Refused the same way, and the alert says the CODE is what
              clashed. This is the case the old build let straight through -
              only the name was ever checked, so any existing code was
              accepted.
 7. Add a department whose name differs from an existing one only by LETTER
    CASE or by extra spaces, e.g. "college of  technology".
    Expected: Still refused. Two rows for one department split its faculty and
              its department average between them, which is the reason for the
              rule.
 8. Edit an existing department, change nothing, and save.
    Expected: Message reads "Department updated successfully". A department
              must never block itself.
 9. Edit a department and set its name to ANOTHER department's exact name.
    Expected: Refused with the same alert. The edit path had no duplicate check
              at all, so this used to succeed silently.
10. Open a department to view its detail.
    Expected: Shows "Department Overview", its "Department Head" (or
              "No department head assigned"), "Instructors (n)" and
              "Dept. Average".
11. Look for a way to DELETE a department.
    Expected: There is NO delete control. Departments are add/edit only, so an
              existing department cannot be removed out from under the
              instructors and results attached to it.

Expected Result : Departments can be added behind an explicit confirmation and
                  edited freely, no name or code can ever be reused on either
                  path, and no delete path exists.
Actual Result   :
Comments        : Steps 5-9 are enforced in the app and, once
                  20240130000019_one_department_per_name_and_code is applied,
                  in the database too. Without that migration the refusals
                  still appear, but only in Dart, so the REST API and two
                  admins saving at once can still create the duplicate.
                  Step 11 asserts intended behaviour, not a missing feature. If
                  a delete control HAS appeared, that is a regression against
                  the no-delete decision.

TC-A11  SYSTEM SETTINGS - SWITCH THE ACTIVE ACADEMIC TERM          [LIVE DATA]
================================================================================
Preconditions : Drawer item "System Settings" is reachable. A second device or
                account signed in as an instructor, to observe the effect.
Test Data     : Edge function [update-system-settings]. Table
                [system_settings].

!! HIGHEST-IMPACT ACTION IN THE SYSTEM !!
   Switching the term changes what every dashboard, report and evaluation in
   the application points at, for every user. Do not run this during a live
   evaluation period.

STEPS
 1. Open "System Settings" and find the "Academic Term" section.
    Expected: Shows the current "Active Semester" and "Academic Year", and
              states that "Changes apply to every dashboard, report, and
              evaluation."
 2. Select a different term and submit.
    Expected: A confirmation step titled "Confirm Term Change" appears. The
              term does NOT change until it is confirmed.
 3. Cancel at the confirmation.
    Expected: The active term is unchanged everywhere.
 4. Confirm the change.
    Expected: The new term is saved via [update-system-settings] and the
              screen shows the new active term.
 5. Return to the admin Dashboard and Analytics.
    Expected: Both now report the newly active term, with figures for that
              term.
 6. On the instructor device, WITHOUT restarting the app, observe the
    instructor's screens.
    Expected: Feedback, Past Terms, My Subjects and Subject Detail all reload
              themselves onto the new term.
 7. Attempt the change with the edge function unavailable.
    Expected: A clear failure is reported, e.g. "Edge Function not found or
              offline:", and the active term is NOT left half-changed.
 8. Switch the term back to the original.
    Expected: Succeeds, and every screen returns to reporting the original
              term.

Expected Result : The active term changes only after an explicit confirmation,
                  propagates to every role without a restart, and a failure
                  leaves the previous term intact.
Actual Result   :
Comments        : Step 8 is mandatory. Leave the system on the term it started
                  on.

TC-A12  ADMIN'S OWN ACCOUNT SECURITY, INCLUDING ROLE CHANGE
        VERIFICATION                                               [LIVE DATA]
================================================================================
Preconditions : Signed in as SAO admin on "System Settings", with access to
                the admin's inbox.
Test Data     : A new password of at least six characters, NOT recorded in this
                document. Edge functions [send-admin-code],
                [admin-update-role].

!! WARNING !!
   Steps 6-9 change this admin's own role. Getting it wrong can lock you out of
   the admin module. Have a second SAO_ADMIN account available first.

STEPS
 1. Find the "Administrator Profile" section and tap "Edit Personal Details".
    Expected: An "Edit Admin Profile" form opens with the name fields, and
              saves successfully.
 2. Tap "Edit Email", submit a valid new address.
    Expected: Message reads "Email updated! Check your inbox for
              confirmation." The old address keeps working until the link is
              clicked.
 3. Tap "Edit Password" and submit mismatched passwords.
    Expected: Refused with "Passwords do not match."
 4. Submit a valid new password with the WRONG current password.
    Expected: Refused with "Current password is incorrect." The password does
              not change.
 5. Submit a fully valid password change.
    Expected: Succeeds and the session is ended, requiring a fresh sign-in with
              the new password.
 6. Attempt to change your own administrative role.
    Expected: The app states "Changing your administrative role requires
              identity verification." and asks "Enter the 6-digit code sent to
              your email:". Only "SAO_ADMIN" and "SAO_STAFF" are offered.
 7. Enter an INCORRECT code.
    Expected: Refused. The role does NOT change.
 8. Enter the CORRECT code and change the role to SAO_STAFF.
    Expected: The role changes via [admin-update-role], and on next sign-in
              the account lands on the Data Gatherer screens with no access to
              admin screens.
 9. Using the SECOND admin account, change the first account back to
    SAO_ADMIN.
    Expected: Succeeds, and the first account regains admin access.
10. Find "Deactivate My Account" and open it, then CANCEL.
    Expected: A warning appears explaining the account can only be restored by
              an SAO Admin, and cancelling leaves the account fully active.

Expected Result : The admin can maintain their own profile, every password rule
                  is enforced, and changing an administrative role is gated
                  behind a correct emailed 6-digit code.
Actual Result   :
Comments        : Step 6 is the important one. A role change that succeeds
                  WITHOUT the code is a critical security failure and should be
                  raised immediately.
